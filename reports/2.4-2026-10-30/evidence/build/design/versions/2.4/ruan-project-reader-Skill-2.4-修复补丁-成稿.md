# ruan-project-reader Skill 2.4 修复补丁（成稿）

> **文档性质**：用户确认的 **2.4 修复实施成稿**，对外版本 **2.4**，工程目标版本 **2.4.0**。本稿确定修复需求与验收标准；**不代表仓库已登记 `approved`、2.4 Skill 已实施、验收用例已执行或正式成品已发布**。设计登记、开发、发布及 Git 操作遵守仓库 `AGENTS.md` 与实际用户授权。
>
> **核对基线**：2026-10-30 查阅 `ruansilver/ruan-project-reader` 的 2.3.0 正式设计和开发源，包括 `SKILL.md`、`references/collaboration.md`、`references/completion.md`、`references/check-format.md`、`templates/STATE.md`、`templates/module.md`、`templates/remote-relay.md`、`scripts/check.py` 及 2.3 验收报告。实施 AI 必须重新核对实际 HEAD、工作区与当前文件；本文不替代实施时的源码核验。

## 一、用户需求与修复边界

用户希望通过**本地 AI 读取真实源码并补证、远端 AI 独立质疑并组织 Markdown/Mermaid、用户人工转交与最终验收**，逐步构建可追溯、可下钻、可恢复的项目理解知识库。2.3 已规定每次远端人工交接必须暂停，但远端交出完整文档之后，尚未形成“本地核验—用户验收—继续授权”的完整后半段。

本次要满足的需求及背后的原因：

1. **远端交稿不等于最终定稿**：远端不能直接读源码。本地须结合当前授权源码、配置和已有候选/未决，对完整稿做适用核验；有问题则向远端反馈并迭代，不能凭一方表示“没有问题”直接完成。
2. **源码核验通过不等于用户满意**：图的阅读路径、布局、短注和表达方式也属于用户验收范围。用户可以向任一 AI 提出意见；新稿仍应由本地按受影响范围核验。
3. **验收与开始下一项是两项不同决定**：用户明确认可了哪个当前稿，才能正式完成该协作单位；用户未明确授权继续，就不得进入下一协作单位。用户一次回复同时明确两项决定时，可分别生效。
4. **人工作业必须能可靠交接和恢复**：待审稿可写入原模块路径，但保存不等于验收。需要保存正在等待的对象、文件版本、核验证据与下一步，避免断线后跳过用户节点。
5. **稿件传递应保真**：远端生成的完整 Markdown 经人工转交本地时，不能因为本地模型重新誊写数百行而悄然变成另一份内容；正式核验应针对用户实际交回的原始稿件。
6. **升级不能抹杀 2.3 成果**：已有大量按 2.3 形成的知识库没有 2.4 用户验收字段。新检查器应识别旧规范、如实给出未验证结果；仅在用户明确启动迁移时，才对存量成果补充验收流程。
7. **修复后的 Skill 必须无痕、统一**：用户反复强调的“东坡肉问题”是：本来要求东坡肉，AI 错做蛋炒饭后，不能交付“东坡肉（去掉蛋炒饭）”；正确结果应直接是一份东坡肉。同理，**本补丁可以记录旧问题与修复依据，最终运行 Skill 只能呈现自然融合的当前有效规则，不能写成历次纠错说明书**。必要的安全与授权约束可以直接表述为现行规则，禁止的是历史错误、旧方案否定和修补过程的残留。

**修复范围**：以 2.3 为基础，仅补充协作后半段及其必需的状态、记录、核验、恢复和检查支持。保留先下研后成文、首轮总览、入口/汇点及时登记、候选逐条处置、父子/公共模块契约、四项闸门、每次人工转交暂停、同仓串行、发现/处置/完成分离、Goal 安全边界及 Mermaid/短注规则。不引入数据库、通用状态引擎、双 AI 自动通信、Figma 实施或业务代码修改；不把静态检查视为源码真实性或用户实际授权的证明。

## 二、已发现的问题与证据边界

下表列出对 2.3 实际规则的静态核对结果及 2.4 必须处理的设计风险；**不据此声称真实项目中已经发生用户授权被绕过**。

| 位置／依据 | 2.3 当前情况 | 需要解决的问题 |
| --- | --- | --- |
| `SKILL.md` 工作循环、`references/collaboration.md` | “远端完整当前稿 → 本地核验、过闸并保存 → 下一项”；已有人工转交暂停 | 本地核验失败后的返回远端循环、用户验收与独立继续授权尚未作为统一末段实现 |

**保留原完成语义**：2.3 四项闸门以“其中阻塞本层”为主要完成阻断条件，**并非要求“问题数一律为 0”**。已经有真实去向且不影响父层边界的子层未决，仍可留待后续处理；“已证叶子”和“范围整体完成”继续适用各自更严格的标准。2.4 不能通过新增验收机制暗中改变这些判据。

2.3 已有 36 项回归及有限隔离样例通过的记录；真实 Goal 自动续跑、真实双 AI 往返、长期恢复及部分平台实机行为仍标为 **UNVERIFIED**。本补丁所有新增规则与验收用例在实施前均属**要求**，不是已发生的验证结果。

2. 通读实际 `SKILL.md`、相关 `references/` 与 `templates/`、`scripts/check.py`、现有测试与构建脚本。将第四节逐项映射为**已具备／需补齐／冲突／待核实**，列出具体落点和预计影响。现有实现若已满足某项，应复用而不重造。
3. 先运行原有回归并保留基线；确认 `check.py` 原有三状态、八项汇总、模块闸门、整体完成以及退出码的具体实现，制定兼容测试。检查是否有 2.3 未验证的 Goal 行为，不能借升级声称已验证。
4. 以本成稿为已确认的 2.4 修复目标，按 `AGENTS.md` 在设计目录登记 **2.4.0 `approved`**（保留既有已发布设计不变），再修改开发源和测试。发布、安装构建以及提交/推送分别按工程规则和用户授权执行；本稿成稿不等于已开发或已发布。

实施中应优先在已有入口、引用资料、模板和检查器内作配套最小修改；**不得为了新增一个人工验收关口建立第二套待办、审批数据库、历史正文库或复杂全局状态机**。

## 四、具体修复

### 1. 补齐远端交稿后的本地核验、用户验收和继续授权

保留 2.3 已有的本地取证、远端质疑、本地逐项补证、远端完整稿及各人工转交暂停。完整闭环为：

**本地取证 → 远端质疑 → 本地补证 → 远端提交完整当前稿 → 本地依据源码和适用闸门核验 → 待用户验收 → 用户认可后正式完成当前协作单位 → 独立决定是否开始下一协作单位。**

- **本地未通过**：保持“梳理中”。指出具体位置、错误/遗漏、实际证据、影响、未决和需要改动的范围；给出可由用户复制转交远端的独立提示词。远端重新提交完整当前稿，附本轮反馈背景与改动范围；本地再次核验。遇到同一问题连续两轮无实质进展，沿用 2.3 停滞规则，不无限反复。
- **本地通过**：保存当前稿、适用四项闸门和核验依据，进入“待验收”；向用户说明明确的文件与版本、拟完成类型、未验证范围及限制，提出**单一目的的当前稿验收问题**并暂停。闸门报告保留对象数、问题数、其中阻塞本层数；不能将“问题数非零”直接判为本层未完成。
- **用户有异议**：可向任一 AI 直接提出。事实、遗漏分支、调用关系、状态、出口或源码依据问题由本地核实；远端不得凭用户一句猜测将其写成已证事实。表达或排版问题由远端组织新稿；若用户先向本地提出，本地负责转交远端，而非跳过既定图文组织职责。需要调整的正式稿无论由谁接收反馈，都须经过适用的本地复核。
- **用户认可**：只作用于明确列出的交付文件及对应读者内容版本。本地记录用户实际回答与已验收的文件清单/版本，按合法的拟完成类型转正。验收提问中展示每份文件指纹的前 8–12 位，完整 64 位指纹保存在对应验收记录；仅认可当前稿并不赋予开启下一协作单位的权限。
- **继续授权**：在当前协作单位完成之后，只有收到用户明确允许继续的指令才可开始下一协作单位。用户若在一次回复中明确表示“本稿通过，开始下一项”，两项决定可以分别生效；不默认扩展为后续连续授权。

每次需要用户复制材料或作验收决定时，本地都应保存工作现场并结束本次自主执行；远端交接同样如此。Goal 等自动续跑目标止于最近的人工交接、验收或继续授权关口，实际无法可靠停止时报告限制并停止该模式；真实 Goal 行为未经实测不得宣称 PASS。

### 2. 增加“待验收”状态，保留既有完成判据

模块状态合法值为：**梳理中 / 待验收 / 本层完成 / 已证叶子**。`待验收` 是本地已完成适用事实核验、当前稿尚未取得用户有效认可的过渡状态；**保存文件与进入待验收都不等于正式完成**。

- `梳理中 → 待验收`：已收到本轮必要的远端实际输入及完整当前稿；本地按源码、有效配置、候选/未决和适用闸门核验，确认不存在仍阻塞本层的问题，记录拟转正类型。拟为“已证叶子”时还须满足原叶子额外条件。机械指纹暂不可计算时按第 5 项保持待验收、标记“未验证”，不得转正。
- `待验收 → 本层完成 / 已证叶子`：用户对相同交付版本明确认可，指纹和必要机械检查有效，验收记录齐备，其他原有完成条件仍满足。
- `待验收 → 梳理中`：用户提出需要修改当前稿的异议；或待验收稿的读者内容改变、事实证据失效、发现仍会影响本层陈述的遗漏。重新修订、适用核验后方可再待验收。
- `本层完成 / 已证叶子 → 梳理中`：后续事实、源码/有效配置变化、依赖影响或用户提出的实质修订要求使当前陈述需要修改；沿用 2.3 的重开与受影响引用检查，原验收不能自动批准修订稿。纯运行记录、原始任务处置与派生汇总变化，若不影响读者内容和本层事实，不触发无意义重开。

`STATE.md` 保留“当前焦点、下一步”与由原始文件派生的汇总，2.4 增加**待验收模块数**。`限制：有/无` 属于用户确认的交付条件：其值变化会改变指纹并使对应旧验收失效；`限制说明` 的操作性记录可更新，但若揭示新的实质性限制或影响已认可陈述，必须主动重开并核实。恢复时优先处理当前未完成的人工验收/继续授权，未经授权不能自行切换下一协作单位；但可登记新发现并处置与当前事实真实性直接相关的问题。

**暂停不妨碍发现**：新增入口、汇点、待办等若只更新 `COVERAGE` 或工作记录且不改变待验收模块的读者内容、不影响本层结论，可保持待验收；若补证修改了该模块读者正文，或发现影响其关键边界，则先退“梳理中”。不得为避免回退而漏登记新入口或汇点，也不得借登记发现作为启动下一协作单位的许可。

### 3. 完整 Markdown 默认以文件回传，避免模型重写造成保真损失

远端提交完整当前稿时，**默认由用户保存为 UTF-8 Markdown 文件并将文件或可访问的本地路径交给本地 AI**。本地将收到的原始文件作为待核验输入，直接读取或用文件工具复制到隔离暂存位置；不得先靠模型复述一遍再将复述结果视为远端原稿。核验、diff 和指纹必须针对已明确收到的稿件内容，覆盖到知识库正式路径前先完成比较。

确实只能从聊天复制粘贴时可以兜底：本地要说明这是粘贴回传、明确完整稿边界，尽量以原始文本保真写入临时文件并核对内容；如果无法证明落盘稿与用户提供的完整内容一致，应标记**传递保真未验证**，请用户核对临时文件，不能把重新誊写的文件冒充原稿。用户确认后再按同一核验流程处理；传递完整性与正文验收指纹是两个不同检查。

转交提示词仍单独放明显的 Markdown 代码块，**沿用 2.3 `templates/remote-relay.md` 的外层 `~~~~text` 围栏约定**，以便安全包含内层使用三反引号的 Mermaid 代码块；只有确实不能直接传文件时才把完整 Markdown 放在外围栏内。不要同时强制另一套四反引号规范，也不要让外层围栏混入实际模块 Markdown。

远端还应提供给本地的简短转交说明：用户/本地本轮提出什么意见、修改了哪些部分、哪些事实与未决仍须核实。这些说明属于**转交材料**，不写入模块执行正文，也不作为远端稿件准确性的替代证据。

### 4. 每个文件各自绑定验收记录和读者内容指纹

保留每模块一份权威当前 Markdown；在模块内以一个简洁的 `## 验收记录` 区块记录本文件当前有效的审批信息。2.4 的最小字段：

- **拟完成类型**：`本层完成` 或 `已证叶子`；待验收时先填写，转正后保持其语义。
- **读者内容指纹**：第 5 项定义的 SHA-256；未取得时如实标记未验证。
- **核验基准**：本地实际核对的源码版本与相关有效配置定位、适用本地核验结果和闸门记录位置；证据无法确认时明确写 `基准未知`，不得把沿用既有技术核验写成此次重新阅读或核验通过。
- **用户验收问题与回答**：本次针对**同一内容版本**的单一目的提问（展示文件名、指纹前 8–12 位、限制/未验证范围），及用户实际回答原话或可复核会话位置；未取得时写“未取得”，不得推测或伪造。完整 64 位指纹按本文件记录，不以短前缀进行机器一致性判定。

当一次验收覆盖关联子网内多份**明确列出的文件**时，**每份文件分别保存自己的拟完成类型、指纹和验收记录**，可共同引用同一个用户验收提问/回答位置。不得将所有子文件指纹集中写进一个主文档，以免某子文件重开时反向修改无关主文档的验收记录；用户只认可部分文件时，仅这些文件可转正，其余仍待验收，不能推定同批其他文件已获同意。

“用户是否允许开始下一项”属于工作流程决策，与文件验收相互独立。`STATE.md` 的当前焦点/下一步可记录当前是否在等待继续授权以及对应用户指令位置，供恢复使用；**不引入范围授权、跨多轮自动放行、撤回条件库或第二套长期审批事实源**。没有明确继续授权，保持暂停；一次回复可明确同时完成验收和继续决定。

### 5. 用排除清单定义读者内容指纹，提供可复算的只读工具

**指纹目的**是确保用户认可的实际阅读内容没有被悄悄换版，而不是追踪候选调查、闸门计数或工作现场的每次操作。采用**明确排除清单，其余正文一律纳入**，避免以后新增 `## 补充` 等读者章节时因为未加入白名单而阻塞验收或被静默忽略。

- **完整排除的二级标题区块**：`## 候选记录`、`## 闸门记录`、`## 核验与下一步`、`## 未决`、`## 限制说明`、`## 验收记录`。区块包括标题行及其正文，直到下一个真正的二级标题或文件末尾；排除只作用于这些**标题匹配的整个区块**，不按文内关键词删除个别行。
- **顶部字段**：位于首个二级标题之前的 `状态：…` 整行不纳入；`限制：有/无` **以规范化的 `限制：有` 或 `限制：无` 原样纳入**。状态变化不会仅因字段变化引起指纹失配，限制值变化必然引起失配。状态、限制缺失/重复或限制非法按原格式规则报错，不能因指纹排除而跳过。
- **其他内容全部纳入**：唯一一级标题、一级标题至第一个二级标题之间除状态行外的所有文字，以及未在排除清单中的每个二级标题及其整块正文，包括 `## 职责与边界`、`## 执行图`、`## 逐节点短注`、`## 必要规则与源码依据`、`## 下钻、引用与外部去向`，以及今后新增的正常读者章节。先前一级标题上方若存在非空内容，不得静默丢弃；应按实际内容纳入，或在违反模板契约时明确报未验证。

**正文与待办的分界**：已核对的 2.3 模板使用 `## 未决` 存原始未完成任务、`## 候选记录` 存候选处置，二者应承接**可变的待办行、调查进度、下一动作和处理状态**。`## 必要规则与源码依据` 保存读者需要知道的已证事实、重要未证边界及其对理解的影响，不能把日常反复增删的待办流水行塞在这一节造成无意义的指纹变化；也不得为了稳定指纹，把会影响读者理解的事实、限制或未知说明移到排除区。读者正文的实质陈述有变化就应重新核验和验收，不能通过修改节名规避。

**统一规范化与计算契约**（规范、命令实现、正常检查和测试必须完全一致）：

1. **读取**：以 UTF-8 严格解码；只移除文件起始的一个 UTF-8 BOM；将 `CRLF`（`\r\n`）替换为 `LF`（`\n`）；若仍有孤立 `CR`、解码错误或不支持的编码，输出 **UNVERIFIED** 和具体原因，不产生有效指纹。既不全局折叠空格，也不对正文做 Unicode 规范化、排版或 Markdown 渲染。
2. **识别真实标题及围栏**：按 CommonMark 风格的 ATX 标题和 fenced code block 规则扫描行。标题必须在围栏之外，起始缩进最多三个空格，`#` 数量为 1 或 2，后接空格/制表符或行尾；标题名去除 ATX 可选尾部 `#` 装饰并修剪两端空白后用于匹配固定标题，但**输出指纹仍保留原始标题行**。围栏起始缩进最多三个空格，由至少三个连续反引号或波浪线构成；以缩进最多三个空格、相同围栏字符、数量不少于起始围栏且其后只有空格/制表符的关闭行结束，反引号起始围栏的信息串不得含反引号；围栏内出现的 `## ` 仅是代码文字，不得切分章节。无法闭合的围栏或无法可靠解析的结构报 **UNVERIFIED**，不能猜测二级标题边界；缩进四空格及以上的代码行不当作 ATX 标题。
3. **切分**：在围栏外确认唯一一级标题与 2.3 模板的必需二级标题，各必需标题必须唯一；六个排除节出现重复或与固定结构歧义时也报未验证。一级标题和首个二级标题之间的文字组成“前置片段”，仅删除其中唯一的 `状态：…` 行，保留 `限制：有/无` 的规范化行和所有其他原文。其他片段从其 `##` 标题行开始，直到下一真实二级标题之前；剔除上述六个排除片段，**不限定剩余二级标题的名称**，保留它们在文件中的实际次序。缺失必需结构时按可确定的错误报 FAIL 或无法解释时报 UNVERIFIED，绝不输出看似有效的部分哈希。
4. **拼接和哈希**：保留每个纳入片段的行内空格、缩进及内部换行；仅对各纳入片段去除末尾多余的 `LF`，片段之间以**两个 `LF`** 连接，最后追加**一个 `LF`**。对最终 UTF-8 字节流计算 SHA-256，输出小写 64 位十六进制。相同逻辑在 `--fingerprint`、正常 `check` 和项目级指纹生成中复用，不得维护三套算法。无效围栏、重复关键标题、歧义字段均不提供“成功”的哈希。

增加只读命令 `python3 <Skill目录>/scripts/check.py --fingerprint <模块文件>`：仅打印文件定位、规范化版本/算法标识及实际 SHA-256（或明确的失败/未验证），不写回文件或转换状态。本地 AI 必须**实际调用可信工具取得指纹并照实引用**，不得凭空构造或心算 SHA-256。正常 `check.py <project-map>` 重算完成模块指纹并与记录比较：已完成模块缺必需验收字段、记录的合法指纹与当前内容不一致等确定性违规报 **FAIL（退出 1）**；解析或计算未能完成时报 **UNVERIFIED（退出 2，且没有其他 FAIL）**。指纹不能证明本地是否真的重读源码或用户是否亲自同意。

**缺少 Python 3.10+ 或其他能够执行同一算法的可信计算工具时**，仍可进行源码调查、保存模块草稿和进入**待验收**，但指纹标记“未验证”，即使用户表示认可也不得标为“本层完成/已证叶子”。工具恢复后重新获取有效指纹、核对当前文件并向用户再次确认该具体版本，方可转正。**Python（或可信等效实现）只对 2.4 正式转正和整体完成成为必要能力，不妨碍只读调查或阶段性草稿。** 这一门槛须在 `SKILL.md` 与使用者可见的 README/安装说明中提前明示。

### 6. 用户验收话语、异议与差异复核

向用户提出的验收请求须**单一目的**且指向当前文件名（关联子网则列明全部文件）与读者内容版本。例如“这组 Markdown（A：指纹前 10 位…；B：指纹前 10 位…）已按所列技术核验与限制交付，是否认可其作为本轮当前版本？”；**指纹前 8–12 位只用于用户辨认，实际验收与机器校验绑定各文件完整 64 位值**。不要把“是否验收”和“是否继续”揉成必须回答“是”的单一问题。

用户的回答按语境判断：在上述明确问题后回答“可以”“通过”可以构成当前稿认可；“不错”“再看看”等泛泛评价不自动构成授权。**带条件的认可**（如“可以，但第二张图改一下”）属于**修改异议**，不转正；先修订并再次核验，之后重新取得对新稿的无条件确认。若用户在一次回答中明确增加“并进入下一项”，在验收成立的同时可以记录独立的继续授权。

远端每次修订应提交**完整当前稿**及简短修改范围说明。本地在覆盖实际当前模块文件前，应**自己对比**旧稿与新稿，包括远端没有声明的连带变化；可使用临时文件和一次性 diff，不要求在项目知识库保存修订历史。

- **纯表达、布局变化**：核对节点集合、边与分支、条件/出口、短注语义、源码依据、引用链接及 Mermaid/适用检查是否仍成立。确认语义未变时不需重复全仓源码调查；但新稿仍需对应版本的适用核验和用户确认。
- **事实、执行关系、边界契约、源码依据变化**：由本地调查受影响源码、有效配置、父子及公共引用，更新候选和未决、重做必要闸门；不能凭用户或远端的猜测直接写入已证结论。
- **仅候选、闸门、未决或 `STATE` 工作记录变化**：不因操作性记录改变就自动让读者正文指纹失效；但 `限制：有/无` 字段变化不属于纯运行记录，应触发重新验收。仍须判断变化是否揭示了影响已验收叙述的事实；若是，按照重开规则复核，而不是仅看哈希是否相同。
- **影响无法判明**：记录未验证范围，按事实风险继续补证；改动小不代表语义风险小。

每次修改都进行适用核验，但适用核验**不等于每次全量重读源码**。已经过用户验收的读者正文如被修改，原验收不适用于新稿；先回到“梳理中”完成受影响复核，再进入“待验收”。

### 7. 已验收模块重开与项目整体完成的人工关口

后续事实或用户意见实质影响某个已完成模块的入口、规则、结果、可达出口、限制值或源码依据时，本地依据真实变化确定**受影响范围**：检查涉及的执行链、调用方、后继及共享模块引用；不强制重新检查无关项目。若无法判断范围，保留未验证并继续调查。受影响模块按原重开规则退回“梳理中”，更新内容、核验后重新待用户验收；不得静默替换已认可稿。

项目整体完成仍须符合 2.3 的正向入口、反向汇点、盲区、实际未决与**全项目四项闸门**要求。**整体交付清单内每份模块文档（包括 `modules/00-总览.md`）必须先分别达到“本层完成”或“已证叶子”、持有当前有效的单文件用户验收记录，且读者指纹与现稿一致。** 任何仍为“梳理中”或“待验收”的文件都不能被整体确认顺带批准；整体清单不得故意排除本轮范围内的未完成模块来绕过原整体闸门。整体用户验收聚焦覆盖、总览、全局闸门和整组交付范围，**不替代模块逐份验收**。

当全部模块验收与技术闸门均达到要求后，在 `COVERAGE.md` 现有整体记录体系中保存整体待验收范围、明确的模块路径清单、整体指纹、技术核验和用户问题/回答；用户认可之前，`本轮范围整体完成：否`。用户认可当前整体交付版本后方可切换“是”；这不是新增可以跳过四项闸门的状态。

**整体指纹的唯一算法**：对清单中每个模块使用第 5 项的单文件读者内容指纹。路径均采用相对于 `project-map/` 的形式，目录分隔符转为 `/`，随后对路径字符串进行 **Unicode NFC 规范化**；检测规范化后同名/路径冲突并报错。按这些 NFC 路径的 **UTF-8 字节序升序** 排列，不按本地文件系统、语言环境或 Unicode 码点默认比较。每项拼接 `NFC相对路径的UTF-8字节 + NUL(0x00) + 对应文件小写64位SHA-256的ASCII字节 + LF(0x0A)`；按顺序连接所有项，对最终字节序列再取 SHA-256。清单中需覆盖本轮声明范围内的全部模块，包括 `modules/00-总览.md`；不得重复、遗漏或包含范围外文件。`--scope-fingerprint <project-map>` 可以只读生成及复核，输出清单、算法标识和整体 64 位指纹。模块增删、改名、清单范围变化、限制值或其他读者内容变化均导致相应重新检查/验收。

**整体声明失效是流程动作，不是单靠静态哈希就能证明的历史事件。** 任一模块重开时，本地必须同步将整体完成声明置为“否”、使既有整体验收记录失效，并根据真实变化重新过适用闸门；新增入口/汇点、覆盖事实或有效配置变化影响整体结论时亦然。即使之后文件正文恢复为先前哈希，也不得自动恢复完成声明或用户整体认可。`check` 可以验证**当前**文件、记录、指纹和清单之间的一致性，但无法倒推某次重开是否真的执行了撤销动作，也不能证明用户实际授权；这项行为必须另用**状态切换/中断恢复的执行用例**验证，不能用一次静态检查的 PASS 冒充。

### 8. `check`、模板、旧库兼容与用户触发的迁移

在现有文件体系内统一实施，不重造状态引擎：

- **`SKILL.md`**：工作循环只保留“本地核验通过进入待验收；用户明确认可才转正；用户明确授权才进入下一项”的关口及指向 `collaboration.md`、`completion.md` 的链接。入口提前说明正式转正需 Python 3.10+ 或可信等效指纹工具；详细算法、迁移和恢复规则放引用资料，避免把入口写成长篇补丁记录。
- **`references/collaboration.md` / `references/completion.md`**：对齐往返、回退、异议分类、单一验收问题、文件传递、差异复核、完成及整体验收。**`templates/remote-relay.md`** 沿用 `~~~~text` 外层围栏，明确完整稿默认文件交付及独立修改说明。使用者可见的 **`README.md`/安装说明** 同步说明指纹计算能力与转正限制。
- **`templates/module.md`**：新增 `## 验收记录`；保留核对确认的准确标题 `## 职责与边界`、`## 执行图`、`## 逐节点短注`、`## 必要规则与源码依据`、`## 下钻、引用与外部去向`、`## 候选记录`、`## 未决`、`## 限制说明`、`## 核验与下一步`。动态待办记录落在 `## 未决`，候选处置落在 `## 候选记录`；读者必须了解的事实/未知仍写读者正文。模块完成之前核对所有必需标题与排除清单逐字一致，不能凭语义相近的节名假装已覆盖。
- **`templates/STATE.md`**：加入 `规范版本：2.4` 与**待验收模块数**；其余**八项**原统计（梳理中、本层完成、已证叶子、待办、阻塞、入口、汇点、覆盖记录）继续从权威记录派生，总计九项统计。`规范版本` 不作为第十项统计，也不是已安装 Skill 的产品版本。**`templates/COVERAGE.md`** 在整体记录区域保存当前清单及用户整体验收凭据。
- **`scripts/check.py` / `references/check-format.md`**：支持四状态、九项统计、唯一且只读的单文件/整体指纹计算、完成与待验收记录、整体清单及技术闸门的静态一致性。所有检查继续只读；用户实际授权、源码真实性、历史中有没有正确撤销整体验收均属于人工/行为核验。原退出码保持：0 为适用机械检查均通过，1 为确定失败，2 为不存在失败但有未验证。

**旧库识别与兼容检查（默认只读，绝不自动迁移）**：

1. 2.4 结构以 `STATE.md` 中的 `规范版本：2.4`、四状态和九项统计为准。该字段是知识库**数据契约版本**，不替代 Skill 安装版本。
2. 对缺少 `规范版本`、仅含三状态/八项统计且未混用新字段的合法 2.3 结构，按**2.3 的静态规则**检查：发现明确格式或一致性错误仍返回 **FAIL（1）**；无这些错误时也提示“2.4 用户验收尚未验证”，整体返回 **UNVERIFIED（2）**，不因为旧库缺待验收数和验收记录直接判失败。
3. 若混用新旧状态/字段、出现新状态但缺版本，或明确声明 2.4 却缺其必需记录，则按能确定的错误报 FAIL，解析不充分的情形报 UNVERIFIED；不得通过删掉版本声明规避新版检查。
4. 旧格式读取和检查均不得改文件，不把安装 2.4 自动解释为全部旧知识库已取得用户验收。

**由用户明确启动的一次性迁移**：

1. 先说明当前旧库技术状态与缺少的新用户验收凭据，列出整个 `project-map/` 的迁移范围及完成模块清单，**由用户明确指令才执行**。知识库格式迁移以一个 `project-map/` 为原子单位：全部旧完成/叶子模块须先转换为“待验收”或因需补证转换为“梳理中”，旧整体完成改为“否”，并同步更新九项汇总与 `规范版本：2.4`；**用户对各模块的正式验收可以分批进行**。不得只给部分模块补新字段就把整库标为 2.4。提醒用户在迁移前自行提交 Git 或备份到知识库之外作为回退手段；Skill **不在 `project-map/` 内存放历史正文副本**，也不擅自执行提交、推送或覆写用户备份。
2. 对每个旧完成/叶子模块保留原**拟完成类型**，先核对其已有技术闸门与证据记录。源码基准识别顺序为：读取已有基准标识和配置记录；请用户声明自原核验后来源码/生效配置是否变化；若目标项目使用 Git 且有可比较的基准，进一步以模块引用的相关源码文件、配置及依赖影响做差异核对。**Git 文件差异只能支持其实际覆盖的路径，不能自动证明未记录的动态配置或隐式依赖没有变化。**
3. 若已有记录和来源码基准足以支持既有技术核验、未发现矛盾，可默认不重新全量读取源码，将旧完成类型作为拟完成类型切至“待验收”，记录“**沿用既有技术核验记录；本次未重新读取源码**”。若无法判定旧源码基准，明确记录 **`基准未知`**，在单一目的的用户验收问题中明示“无法证明当前源码与既有核验时一致”，**由用户决定是否按既有技术核验成果接受这个不确定性**。用户明确接受时仅确认当前历史成果的交付版本，不得将基准未知写成“已证明与当前源码一致”；用户要求按当前源码核验或有已知相关变化、重大矛盾时，本地必须补证受影响范围，不满足既有完成条件的模块保持“梳理中”，不能靠用户认可越过原技术闸门。
4. 既有“梳理中”模块继续按新版流程处理，不能自动获准。迁移中的旧整体完成 `是` 改为 `否`，在新记录中重新完成全局技术/用户关口；保留原有覆盖事实与有效闸门依据，不冒称已经取得 2.4 用户认可。
5. 初次格式迁移须先使整个库满足 2.4 的状态/记录结构：已满足既有技术条件的旧完成项进入“待验收”，缺证或存在事实冲突的进入“梳理中”，不能把无 2.4 验收记录的旧“本层完成/已证叶子”原样留在已声明 2.4 的库中。之后允许用户分批对明确列出的文件集合一次性确认，各文件分别保留本文件指纹/验收凭据、共用同一用户回答位置；未获认可的继续“待验收”。迁移只改必要状态和记录，不大幅改写读者正文、候选或原始待办。完成规范升级后不得再使用旧格式的宽松检查假装符合 2.4。
6. 完成迁移前后分别运行适用检查，报告旧基准已知/未知、沿用的技术依据、是否受影响、用户确认、未决与未验证；迁移流程中遇到无法从证据推出结论之处，必须显式报告，不能自动填“无变化”或“已核验”。

脚本可以核对当前静态状态、正文/整体指纹与记录契约，不能证明用户实际说过某句话，也不能证明自主代理从未越过人工关口。行为正确性用隔离执行与真实平台试验另证，分别报告 PASS / FAIL / UNVERIFIED。

### 9. “东坡肉问题”：最终 Skill 必须自然融合当前有效规则

**本修复补丁、设计评审和独立验收报告**可以说明旧问题、修复原因和差异；**实际运行 Skill** 则必须像原本就按正确规则编写的一样，只有直接可执行、相互一致的现行要求。

1. 直接改写与本次目标冲突的原条款、例子和流程，形成一条完整正确的执行路径；不能保留旧路径，再在末尾追加“不过这次不能这样”“原来不对”等否定式补丁。
2. `SKILL.md`、`references/`、`templates/`、`agents/`（如有涉及）和 `install/` 正式成品中不得夹带“2.3 曾如何”“2.4 本次修复了什么”“旧方案禁止”“东坡肉/蛋炒饭”的历史纠错叙事。版本号与正常的“不得越权继续”“未知不得当零”等**当前有效约束**应保留。
3. 最小化修改范围，复用既有文件、标题与单一事实来源；删除确实过时或冲突的内容，保留已经正确的源码证据、发现、闸门、转交及恢复规则。不能将旧规则加括号否定后留下来，也不能为了无痕而删除必要的实际限制。
4. 交付前既看独立 diff，也要通读修复后的**完整** `SKILL.md`、全部相关引用、模板、检查器、示例和构建成品，确认入口与细则一致，没有“新规则覆盖旧规则”的残留或两套互斥路径。测试应实际执行当前规则，而非只搜索特定修复关键词。
5. Skill 在项目中生成的正式 Markdown/Mermaid 也只呈现当前有依据的事实。**具体文档的修改背景仅放当次人工转交说明中，不落入 `project-map/` 知识库**；设计/开发过程的独立修复证据按仓库规则存放在开发报告中，不能混入正式模块正文。正常的当前验收凭据、已有技术核验依据和源码未决不属于历史纠错叙事，仍按记录契约保存。开发仓库的设计文件、测试报告与独立 diff 可保留修复证据，但不进入正式安装 Skill。

## 五、小型验收用例

在隔离知识库与修复后的实际 Skill 上执行，保留已有 2.3 回归。每项分别给出 **PASS / FAIL / UNVERIFIED**、输入/命令、结果与可复核证据；模拟用户/远端输入须标明模拟，不能当作真实用户/真实远端验收。下列为**实施要求，不是本补丁已完成的测试结果**。

| 用例 | 可观察通过条件 |
| --- | --- |
| 1. 本地不通过再往返 | 远端完整稿故意缺重要失败出口；本地保持梳理中，明确指出源码证据与修改位置，交回远端；修订稿再次适用核验后才可待验收 |
| 2. 待验收真实暂停 | 本地核验通过后保存当前稿、闸门和拟完成类型；未收到用户验收时保持待验收，重复触发不得开启下一协作单位 |
| 3. 缺用户验收不得转正 | 远端材料和适用闸门完整，`check` 的其他部分合规，但用户确认缺失；强行切到完成/叶子被判失败，实际代理仍停在待验收 |
| 4. 带条件认可不转正 | 用户回答“可以，但把第二张图改一下”，按修改异议退回梳理中；验收记录保留所问问题与用户回答，不因“可以”二字转正 |
| 5. 验收与继续独立 | 单纯认可当前稿只完成当前协作单位并等待继续指令；“当前稿通过，进入下一项”可分别生效，不推断后续长期授权 |
| 6. 多文件验收各自记录 | 用户明确一次验收关联子网中的 A/B；A、B 各自有指纹/记录，共享用户确认位置，无集中指纹真相；只认可 A 时 B 仍待验收 |
| 7. 动态记录不改变正文指纹 | 父层已验收后，子层任务完成仅更新父层 `## 未决`、`## 候选记录`、`## 核验与下一步` 或 STATE；读者正文不变时指纹稳定。若修改 `## 必要规则与源码依据` 中的事实/未知说明则指纹改变并重新核验，不能为过测而隐藏事实 |
| 8. 指纹规范化与只读命令 | BOM、CRLF 与片段末端多余 LF 的等价稿指纹一致；CommonMark 反引号/波浪线多长度围栏内 `##` 不切段，未闭合围栏返回 UNVERIFIED；新增 `## 补充` 默认纳入，改图/短注/依据/限制值会改变指纹；`--fingerprint` 不写文件且与正常 check 结果一致 |
| 9. 无 Python 的降级 | 缺 Python 或可信等效指纹工具时，待验收稿可保留但指纹未验证；即使有用户认可也不能转正，不编造 SHA，报告 UNVERIFIED |
| 10. 文件与粘贴回传保真 | 同一完整远端稿以文件、粘贴两种方式交回，若原始文本等价则暂存内容一致；粘贴发生截断/悄改时可发现或明确报传递保真未验证，不把重写后的文件冒充原稿 |
| 11. 表达类反馈 | 远端提供完整新稿和修改说明，本地自行做 diff，核对边/条件/出口/引用/短注语义；只改变表现时不强制全仓重查，但仍走新稿验收 |
| 12. 事实类反馈与状态回退 | 用户指出遗漏入口/失败出口，本地补证后修订图文和候选、重做适用闸门；待验收期间若改模块正文先退梳理中，不能凭用户意见直接改为已证 |
| 13. 待验收期间登记发现 | 新入口/汇点仅需更新 COVERAGE 和待办、未影响当前模块读者陈述时可保持待验收；若影响当前陈述则回退梳理中；不隐瞒发现也不借机启动下一单位 |
| 14. 已完成模块重开 | 后续事实影响已验收稿时，仅受影响模块重开、原验收失效，复核后重新获取用户认可；无关模块不被反复重审 |
| 15. 项目整体验收与指纹 | 清单含总览及全部范围内模块，模块未个别验收或指纹失效则整体不能转正；NFC 路径、UTF-8 字节排序、路径冲突及整体哈希可复算。另以**执行测试**证明模块重开或覆盖变化时即时撤销整体完成，即使哈希恢复也不自动恢复；不能只用静态 check 证明撤销曾发生 |
| 16. 旧 2.3 库只读兼容 | 对合法的三状态/八字段旧库运行新版 check：不修改文件，返回 UNVERIFIED（2）并说明未启用 2.4 用户验收，而非整库 FAIL；旧库已有明确结构错误仍返回 FAIL（1） |
| 17. 用户显式迁移 | 无用户指令不迁移；迁移前提示用户 Git/外部备份。整个库一次性调整为合法的 2.4 状态/字段，模块人工验收允许分批；保留旧拟完成类型、候选和覆盖。按可证范围核对技术依据/Git 差异，基准不明则记 `基准未知` 并由用户明确决定是否接受，已知相关变化须补证；不得伪造新核验 |
| 18. 原有完成判据与汇总 | 2.4 统计为原八项＋待验收一项，`规范版本` 非统计；2.3 旧八项可只读兼容；父层“问题数非零但阻塞本层为零”仍可完成，叶子未处置/限制及整体覆盖门槛不被改变 |
| 19. 暂停与 Goal 恢复 | 无新材料时重触发不修改审批结果或自行推进；真实 Goal 终止、重新触发、意外中断恢复如未实测分别记 UNVERIFIED，普通模拟不代替真实平台验证 |
| 20. 无痕融合与原回归 | 现有有效测试继续通过；`SKILL.md` 与 README 前置说明 Python/可信等效指纹依赖；最终 Skill、模板与安装包无历史纠错、旧新两套规则、双套围栏或额外状态系统，独立 diff 仅保留必要修改 |

以上用例为 2.4 **实施验收要求**；在 2.4 实施前**均为 UNVERIFIED**。关键用例失败或未验证时须如实列出，不能宣称全部验收通过；如用户另行决定带限制发布，必须保留真实限制，不能把发布决定当成测试 PASS。

## 六、依据、交付与适用范围

**依据**：

- [ruansilver/ruan-project-reader](https://github.com/ruansilver/ruan-project-reader) 当前 2.3.0 正式设计、开发源与已发布安装体系；实施以实际仓库 HEAD、`AGENTS.md` 和已确认目标版本为准。
- 2.2 基线设计、2.3 正式设计与 2.3 修复补丁；用于确认已有的源码取证、完成闸门、人工暂停及无痕维护边界，历史已发布设计保持原样。
- 用户对“远端完整稿—本地源码核验—用户验收—授权继续”及“东坡肉问题”的明确需求，以及本轮关于指纹边界、传递保真、兼容迁移、精简授权和检验场景的评审意见。评审意见属于设计建议，不替代实施事实。

**实施交付**须包含：基线与实际修改文件清单、独立 diff、原有及新增测试的逐项结果与证据、指纹算法与命令实测、旧库兼容和迁移边界、人工验收与真实 Goal 的未验证范围、最终 Skill 全文无痕审查、`src/` 与正式 `install/` 的版本/哈希对应关系以及剩余限制。2.3 既有设计与正式安装成品保持不变，直到按 `AGENTS.md` 完成 2.4 设计登记、开发验证和明确授权的发布流程；开发完成不等于自动授权发布。

**实施验收重点**：待验收保持原完成语义；指纹按统一算法可重复计算，含 `限制：有/无` 并对新增正文默认纳入；围栏解析、整体验收清单与 NFC 路径排序明确；完整稿文件回传与当前审批版本一致；旧库可只读检查、迁移不伪造源码基准；各模块先验收再做整体交付确认；整体重开失效由行为用例验证；最终 Skill 仅保留当前有效规则。
