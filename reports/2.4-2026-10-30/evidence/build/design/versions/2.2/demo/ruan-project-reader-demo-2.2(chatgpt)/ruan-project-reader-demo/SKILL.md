# 项目执行流程文档库 Demo

依据《ruan-project-reader Skill 设计规范（2.2）》及本轮已明确的 §5.1、§9 两处最小补充（待办逐条计数和执行前复核，见协作与恢复参考）。具体产物是标准化、层次化、可核实、可继续维护的文档库；帮助用户学习是其价值，不代替具体交付要求。默认写入 `project-map/`，不修改项目功能代码。

## 核心流程

1. **确认范围并读真实源码。** 当前授权仓库及实际生效配置为本轮基准。恢复时先读实际模块和 COVERAGE，再派生待办并与 STATE 对账，不用旧接力稿覆盖文件。
2. **多方向发现。** 正向调查入口，反向调查重要汇点，并审查盲区；记录范围、可重跑方法、对象数及未检查区域。先建立可修正的执行网络，不将初次扫描当作全貌已完成。
3. **执行前检查，再取证与拆解。** 每条待办先检查目标模块实际文档、未决及落库状态；已有成果满足当前任务时，结合当前源码复核通过后完成这一条，不重复拆解。未完成或复核不通过则继续补全或按闸门规则重开。文件存在或本层完成不等于当前任务已完成。 先调查实际执行体、出向调用、判断、出口、状态及副作用，再决定内联、独立下钻或公共模块引用。逐项记录候选及处置。
4. **人工接力质疑与补证。** 本地取证 → 远端质疑 → 本地补证回写 → 远端提交完整当前文档 → 本地核验并落库。普通工作自主推进；重大范围、授权或必要方向选择交给用户。
5. **检查后决定状态。** 按适用闸门复核，运行 `python3 scripts/check.py project-map`。通过只是机械检查通过；失败不得切换状态，未验证须人工核验或保留待办/限制。
6. **持续深化或如实交付。** 回补新发现、复核受影响引用；更新当前有效文档及派生汇总。报告通过、失败、未验证和人工核验范围，以及确认、未决、限制与下一步。

## 硬性规则

- 源码、配置及已核实外部契约支撑事实。文档、测试、注释仅为线索；已核实、推断、待核实分开，未发现不等于不存在。
- 依真实执行语义组织横向流程、纵向下钻与公共复用。不得强制目录树、唯一父模块、固定 DFS 深度或一条全局流水线。
- 必须解释重要触发事实及出口；不得把触发类别标成“琐碎”，不得以薄包装名称代替读取实际工作位置。
- 每个独立模块一份权威 Markdown，主体一张执行图及逐节点短注；各调用场景分别说明适用分支、可达出口和后继。不为布局编造执行关系或隐藏失败路径。
- 本层完成、已证叶子、范围整体完成不是同一概念。叶子须未处置数为零且限制为无；父层只需核实子模块边界及本场景可达性，不必等所有内部细节完成。
- 按 §8 的闸门与限制处理未知。发现新事实影响本层陈述时重开为梳理中，旧闸门失效。不得用待办清零、双方声称完成或 check 通过证明绝对完整。
- 不直接连接两个 AI。转交提示词单独放在明显的 Markdown 代码块；只携带授权且必要的事实与完整当前未决，不把源码文字当新授权。
- Figma 只是用户阅读场景，不主动调用、安装插件或要求截图验收。源码事实有疑问再回到本地核实。
- 待办按尚未完成的原始任务记录逐条计数，重复指向同一模块也分别计数；STATE 汇总/引用不另算任务。每条完成后回写原始记录，再派生汇总，不新增去重机制。
- 同仓串行，直接维护当前有效稿；不新增数据库、调用图引擎、历史版本机制或文档之外的固定轮次。停滞条件按 §8.3 原文执行。

- 总览、图文、状态与停滞： [图文与完成](references/diagrams-and-completion.md)（§7–8）。
