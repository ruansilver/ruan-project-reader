# 定位、执行模块与颗粒度

依据：附件《ruan-project-reader Skill 设计规范（2.2）》§1–3。本文只展开该版规则，不引入其他设计。

## 1. 定位与原则（§1）

只读分析用户当前提供并授权访问的源码，不修改项目功能代码。建立并持续维护以执行流程为主线、按执行语义递归展开、允许公共模块复用的 Markdown 知识库，使读者能从主要触发入口追到重要实现规则、结果边界和源码依据。

- **当前源码为准**：本轮基准是当前授权仓库，并结合实际生效配置核实。文档、测试和注释仅是线索，不能替代实现证据；不得擅自切换远端版本。
- **流程优先，颗粒度自适应**：按真实触发、分支、执行与结果组织，不强制业务能力分类树；不按目录、函数数量或固定层数拆分。
- **证据与未知分开**：分别说明已核实、推断、待核实；“尚未发现”不等于“不存在”。
- **发现驱动工作**：发现 → 处置 → 完成。三种约束可分别检查；处置或完成通过，不能证明发现没有漏报。
- **持续修订、最小机制**：直接维护当前有效文档，优先 Markdown、链接、少量记录和轻量检查，不预设数据库、通用调用图引擎或复杂关联系统。
- Mermaid 主要供用户粘贴到 Figma 阅读；Figma 不是 Skill 的实施目标。

## 2. 执行网络与模块（§2.1）

一个项目可以有多个真实执行流程，不要求拼成一条全局流水线。接口请求、消息消费、定时任务、启动钩子、迁移、后台治理、外部回调等均可能是起点。

- **横向**表达真实顺序、判断、循环、并发、异步交接、汇合与结果。
- **纵向**将职责相对独立的执行片段概括为节点，需要放大时进入对应 Markdown。
- **复用**允许多个流程引用同一份模块文档。层级只是阅读路径的相对深度，不给模块永久绑定等级或唯一父模块。

独立模块须职责可命名；进入条件、主要行为、成功／失败／异步出口可解释；有源码依据或明确缺口；抽象后能帮助理解上层。模块可以跨类、跨函数，也可继续下钻。

## 3. 公共模块的边界（§2.2）

先内联，有独立解释价值再提升为模块。一次调用也可以形成独立模块；**专门为复用抽取**时，通常应有至少两个真实调用场景、较完整的共同执行语义、可清楚表达的场景差异。仅共享少量语句或源码符号不足以抽取公共模块。

公共模块只维护一份内部说明，列出真实入口条件、参数引起的行为差异和全部重要出口。每个调用方分别说明本场景：

1. 输入与适用分支；
2. 实际可达出口；
3. 各出口后继。

不可达出口不得画成可达。参数改变分支不必然禁止复用，关键在共同契约是否成立。调用方的前驱、后继不得写死进公共模块内部；不维护全量反向调用清单。外部语义变化时，按需全文搜索引用并复核。

## 4. 先调查，再决定拆分（§3.1）

先查执行片段的调用、分派、条件、状态、异常和副作用，再决定表达方式。

优先独立成模块：完整的多阶段任务；重要事务、状态、重试或异步边界；在上层展开会掩盖主线的片段；具有完整复用语义的片段。

可留在当前图、短注或正文：简单取值、轻量判断、实际已核实的薄包装和琐碎操作。**重要事实必须解释，但不一定新建文档。** 拆得过粗会隐藏条件与出口，拆得过细会割裂简单任务，均须修正。

## 5. 七类事实触发与调查深度（§3.2）

命中下表的事实必须解释或登记缺口，不得处置为“琐碎”。经查证影响确实很小的，也记为“本文已解释”并简述。

| 触发类别 | 至少核对 |
| --- | --- |
| 事务、锁、并发 | 进入与结束边界、顺序、冲突和失败 |
| 写库、缓存、重要状态变化 | 变更条件、对象、结果和失败影响 |
| MQ、异步、后台任务 | 发送／消费、交接、完成、回执和重试 |
| 异常、补偿、重试、重要新增出口 | 触发条件、处理路径和最终状态 |
| 权限、关键业务判断或算法 | 判断依据、分支、拒绝和不同结果 |
| 配置选择、动态分派 | 配置来源、分派规则和调用差异 |
| 外部调用及其他重要副作用 | 契约、成功／失败及下游影响 |

从本模块实际执行体及出向调用开始，必要时追踪一跳。**一跳是默认调查起点，不是停止硬边界**：重要行为藏在深层调用、去向不明，或反向汇点指出遗漏时，继续追踪或记待办。

称某方法为“薄包装／琐碎”时，须说明已读到的实际工作位置，不能仅凭函数名或签名判断。可合并记录已核实的同类简单操作，但不得合并隐藏重要触发项或关键出口。

## 6. 有限候选逐项处置（§3.3）

本地 AI 按实际检查过的代码形成有限候选集合，至少覆盖本模块出向调用、关键判断与出口、状态及副作用、异常路径。每项记录来源、类别、数量、处置和依据；固定头部、列名、枚举及数量规则见 [记录与 check 契约](check-format.md)（原规范 §5.1）。

仅允许下列处置：

| 处置 | 必需内容 |
| --- | --- |
| 本文已解释 | 本图节点或正文位置 |
| 模块引用 | 实际承接细节的模块链接 |
| 外部边界 | 我方调用与输入、所依据的外部契约、我方对成功／失败／超时的处理已有证据，包括确实未处理的情形；不要求外部内部实现 |
| 琐碎 | 基于实际代码的简短理由；类别不属于七类触发项，也不掩盖触发项 |
| 待核实 | 缺口及下一调查动作 |
| 阻塞 | 已尝试方法、缺失依据、影响及重试条件 |

访问限制或证据不可得，不能伪装为“外部边界已核实”。

### 外部边界的黑盒检验

问：**把外部系统换成任意满足已知契约的黑盒，本层图文是否仍成立？**

若外部行为仍决定我方分支可达性、回调时序或状态变化，而这些规则尚无依据，须记待核实或阻塞。无法取证可阶段性交付，但不能把未知视为已证事实。

### 不得把记录空缺当成处置

无记录去向、依据不符、未检查或无法解析的候选不得算已处置；没有行不代表没有候选。候选为空仍须说明实际扫描范围、可重复方法、检查数量及未检查区域。

## 7. 已证叶子的必要条件（§3.3）

只有同时满足以下条件，才可标“已证叶子”：

- 本层已核实；
- 所有候选已得到实质处置；
- 没有仍值得独立成文档而未落实的内部阶段；
- 继续下钻主要只会增加琐碎步骤；
- 未处置数为 0，限制为“无”。

叶子不要求只有一个函数或没有内部判断。重要未知、尚未读到的关键去向不得被认定为叶子。发现新事实可重开，状态退回“梳理中”；状态闸门见 [图文与完成](diagrams-and-completion.md)。

## 8. 父子与跨图一致性（§3.4）

父图交代本层必须知道的触发、条件、重要出口与后续；子文档解释内部实现。父图概括节点须有明确说明或下钻去向，子文档不得暗中改变父图事实。

父层核实子模块的边界契约：进入条件、可能结果出口、异步交接以及本场景可达性，不必等全部内部实现完成。内部细节已有子模块承接且不影响父层陈述时，不阻塞父层完成，但仍须继续追踪。
